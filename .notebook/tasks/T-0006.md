## Brief
# T2b: Project refusals in schedules, workflows, background refresh and fallbacks

## Goal

Since T-0004, a self-hosted paid DataForSEO call refused by its project's ledger throws `AppError("PROJECT_BUDGET_EXCEEDED")` or `AppError("PROJECT_DATAFORSEO_PAUSED")` before anything is sent. Make every multi-step and background path treat that as an expected, terminal condition for the run: stop issuing further paid attempts, keep partial results, record a distinct skip reason the user can see, advance schedules normally, never treat it as a provider failure that triggers a fallback.

Facts with file:line for every site below: report `/home/nicoeft/workspace/webbzi/open-seo/.notebook/reports/T-0002-a1.md` §3 (refusal handling) and §4 (workflow DB scope). Read it first. T-0004's report: `/home/nicoeft/workspace/webbzi/open-seo/.notebook/reports/T-0004-a1.md` (its "Open points" list the paths this task owns). Use `isProjectDataforseoRefusal` from `src/server/lib/dataforseo/projectBudgetRefusal.ts` to recognise the two codes. Design: decision `dataforseo-project-ledger`. The ledger service is `src/server/features/projects/services/ProjectDataforseoBudgetService.ts` (`getProjectSummary(...).status` is `available | paused | monthly_limit_reached | total_limit_reached`).

## Change

1. **Pre-checks where hosted already pre-checks credits.** In self-hosted mode, at the same points that run the hosted credit check (`RankCheckWorkflow.ts` prepare step; AI visibility `startRun` in `aiVisibilityRuns.ts`), read the project summary and, when it is not `available`, refuse with the matching code the same way the hosted path refuses `INSUFFICIENT_CREDITS`, so the existing skip machinery records it. This is advisory (the client gate stays the enforcement), so it is a read, not an admission. The DB read must run inside the step's `pgStep` scope.
2. **Rank tracking** (`RankCheckWorkflow.ts`, `rankCheckPaths.ts`, `src/shared/rank-tracking.ts`):
   - `RankSkipReason` gains `project_budget_exceeded` and `project_dataforseo_paused`; `markRankCheckRunFailed` maps the two codes to them as it maps `insufficient_credits`.
   - A project refusal inside a live batch, a queued `task_post`, or a straggler/fallback batch ends paid work for the run: no live->queue fallback (`runLiveCheck` find-missing re-run), no queue->live fallback (`runQueuedCheck` stragglers), no further batches. Results already saved stay; already posted tasks keep being collected. The run finalizes with its partial message and the skip reason is recorded (a completed partial run currently clears `lastSkipReason`; make sure the budget reason survives).
   - Schedules keep advancing through the existing claim logic; do not disable the schedule and do not replay missed runs.
   - `src/serverFunctions/rank-tracking.ts` `logAutoActionFailure`: the two codes log at info like `INSUFFICIENT_CREDITS`.
3. **AI visibility** (`aiVisibilityRuns.ts`, `aiVisibilityCollection.ts`, `AiVisibilityWorkflow.ts`, `scheduledAiVisibility.ts`, `aiVisibilitySchedule.ts`): the scheduled catch and the schedule-enable baseline run treat the two codes like `INSUFFICIENT_CREDITS`. A refusal mid-run stops further paid steps (posts, live batches, model batches, reposts), marks the remaining observations failed with that code, keeps collecting already posted tasks, and finalizes as partial/failed with the code as `lastSkipReason`.
4. **Error-to-empty-data catch blocks:** `brandLookup.ts` `rethrowIfBlockingAiSearchError` and `promptExplorer.ts` `mapErrorToResult` rethrow the two codes, so the user sees the refusal instead of empty data or "model temporarily unavailable". `websiteResearch.ts` is done (T-0004: a refusal skips competitors like an outage).
5. **Status surfaces** (client): `RankTrackingDomainList.tsx`, `RankTrackingDomainDetail.tsx`, `PromptTrackingPage.tsx`, dashboard `siteTabParts.tsx` show the project reason with a link to the project's API spending settings tab (`/p/$projectId/settings/api-spending`, landed in T-0005), never "Add credits"/upgrade. MCP `get-rank-tracker.ts` prints a readable reason rather than the raw literal.
6. Dashboard refresh (`DashboardCacheService.readThrough`) already keeps the cache and backs off 5 minutes on a failed refresh; confirm a refusal takes that path and does not retry per render. Change it only if it does not.
