## Brief
# T1: Project DataForSEO ledger: schema, repository, service

## Goal

Self-hosted OpenSEO deployments (AUTH_MODE not hosted) need per-project DataForSEO spend tracking with optional USD caps. This task builds the storage and the service only. Later tasks wire it into `src/server/lib/dataforseo/client.ts` (T2) and build the settings UI and agency overview (T3), so the service API below is a contract: keep its names and shapes, and say in your report if you had to change one.

The design is decision `dataforseo-project-ledger`. Follow its Choice exactly. Background (the owner's plan, optional reading): `/home/nicoeft/workspace/webbzi/open-seo/dataforseo-project-budgets.md`, sections "Product rules", "Minimal data model", "Shared request flow".

## Product rules this must enforce

- Per project: `monthlyLimitUsd` (UTC calendar month) and `totalLimitUsd` (all time), both nullable (null = unlimited), plus `paused`. Both limits apply when both are set. Zero is a real limit meaning no new paid usage.
- Committed spend = sum of `estimatedCostUsd` over `pending` rows + sum of `costUsd` over `completed` rows. `released` counts zero. A cost belongs to the month of its row's `startedAt`.
- Admission of a batch of N estimates refuses the whole batch when paused, or when, for any configured limit, `committed >= limit` or `committed + sum(estimates) > limit`. Otherwise all N rows are inserted. Never partially.
- Two concurrent admissions competing for insufficient remaining allowance must not both succeed. The check lives in SQL after the per-project lock, never in a JavaScript read before the batch.
- A database failure is an infrastructure error, never presented as a budget refusal.
- Every query is tenant-scoped: organizationId + projectId, verified through `projects.organizationId`. A project of another organization must be indistinguishable from a missing one.
- Plain JS numbers (SQLite `real`, Postgres `double precision`). No BigInt, no decimal library.

## Build

1. Schema, both dialects, following existing conventions for ids, timestamps, FKs and project-deletion cleanup (look at how other project-owned tables declare `projectId` and what happens on project delete):
   - `src/db/project-dataforseo.schema.ts` and `src/db/pg/project-dataforseo.schema.ts`, exported through the schema barrels, registered in `src/db/schema-parity.test.ts`, migrations generated with the repo's `db:generate` scripts for both dialects.
   - `project_dataforseo_budgets`: `projectId` PK/FK, `monthlyLimitUsd` nullable, `totalLimitUsd` nullable, `paused` default false, `reservationVersion` int default 0, `createdAt`, `updatedAt`, `updatedByUserId` nullable (null means the row was created by admission, i.e. not configured by anyone).
   - `project_dataforseo_usage`: `id` text PK, `projectId` FK (index on `projectId, startedAt`), `feature` nullable text (existing `CreditFeature` values from `src/shared/billing-credit-features.ts`), `operation` text, `runId` nullable, `actorUserId` nullable, `startedAt`, `estimatedCostUsd`, `costUsd` nullable, `status` (`pending` | `completed` | `released`), `completedAt` nullable. No `expiresAt`.
2. Repository + service under `src/server/features/projects/` (`repositories/ProjectDataforseoRepository.ts`, `services/ProjectDataforseoBudgetService.ts`), service -> repository like the rest of the repo. Writes go through `runBatch` in `src/db/runBatch.ts`, statements built from its `tx` handle.
3. Error codes in `src/shared/error-codes.ts`: `PROJECT_BUDGET_EXCEEDED` and `PROJECT_DATAFORSEO_PAUSED`, plus whatever the code registry requires so TypeScript stays exhaustive (client copy and MCP copy are T2/T3; add placeholder entries only if the type system forces it, using: "This project's DataForSEO allowance has been reached. Review API spending in project settings." and "Paid DataForSEO usage is paused for this project. Resume it in project settings.").

## Service API (contract)

```ts
admit(input: {
  organizationId: string; projectId: string;
  actorUserId: string | null; feature: CreditFeature | null;
  operation: string; runId?: string | null;
  estimatesUsd: number[];            // one per paid HTTP call, >= 0
}): Promise<{ usageIds: string[] }>  // same order as estimatesUsd;
// throws AppError("PROJECT_DATAFORSEO_PAUSED") or AppError("PROJECT_BUDGET_EXCEEDED") on refusal

settle(input: { organizationId: string; projectId: string;
  outcomes: Array<{ usageId: string; feature?: CreditFeature | null } & (
    { kind: "charged"; costUsd: number } | { kind: "released" } | { kind: "unknown" })>;
}): Promise<void>  // one runBatch of guarded UPDATEs (id, projectId, status='pending'); "unknown" writes nothing;
// a provided feature fills a null feature; duplicate settlement is a no-op

getProjectSummary(organizationId, projectId, now?): Promise<{
  configured: boolean; monthlyLimitUsd: number | null; totalLimitUsd: number | null; paused: boolean;
  trackingStartedAt: Date | null;   // earliest usage row
  monthStart: Date; nextMonthStart: Date;            // UTC
  monthRecordedUsd: number; totalRecordedUsd: number; // completed costs only
  inFlightUsd: number;              // pending, startedAt within last 30 min
  estimatedUsd: number;             // pending older than 30 min (reported as estimated)
  monthCommittedUsd: number; totalCommittedUsd: number;
  availableUsd: number | null;      // min over configured limits of (limit - committed), floored at 0; null if unlimited
  status: "available" | "paused" | "monthly_limit_reached" | "total_limit_reached";
  featureBreakdown: Array<{ feature: string | null; recordedUsd: number; estimatedUsd: number }>;
}>
listRecentUsage(organizationId, projectId, { limit, offset }): rows newest first (id, startedAt, feature, operation, status incl. derived "estimated", estimatedCostUsd, costUsd)
getOrganizationSummary(organizationId, now?): one grouped query (no per-project loop) returning per project, archived included with an `archived` flag: name, month/total recorded, in-flight, estimated, limits, paused, configured, status
listUsageForExport(organizationId, { from, to }): rows with project name, ready for CSV, recorded and estimated amounts distinguishable
updateBudget({ organizationId, projectId, actorUserId, monthlyLimitUsd, totalLimitUsd, paused }): upsert; bumps reservationVersion in the same batch so it serializes with admissions
```

Validate limits with Zod at the service boundary: finite, >= 0, at most two decimals, or null. Permission checks (`billing: ["manage"]`) are T3's server-function layer, not this service.

D1 caps a statement at about 100 bound parameters. A rank-check batch can hold dozens of calls, so chunk the inserts as the decision says (first statement decides, follow-on statements in the same batch insert only if the first row exists). Check the largest batch the client can send (`rankCheckBatch`, `trackingLiveBatch` callers) and test at that size.

Check `src/db/pg/retry.ts` (`withQueryRetries`): a retried admission must not double-insert (ids + `ON CONFLICT DO NOTHING` handle this) and must not break the transaction. Postgres runs `runBatch` at READ COMMITTED; confirm in your report why statement 3 sees rows committed by a competing admission that held the lock.

## Tests

Real SQL, following the `*.query.test.ts` libsql pattern (e.g. `src/server/features/rank-tracking/repositories/RankTrackingRepository.query.test.ts`, `src/server/features/ai-visibility/aiVisibilityTestDb.ts`). Test through the service. A few scenario tests that cover several rules each, per AGENTS.md "Testing" (read it):
- monthly + total limits both apply; zero vs null; pending estimates block a later admission; settling at a lower cost frees room; a batch is admitted or refused whole; rows from last month do not count toward this month; paused refuses.
- settle: charged/released/unknown, duplicate settle harmless, pending > 30 min shows as estimated, late settle replaces it.
- isolation: another org's project id is refused / not readable.
- concurrent admission: two admissions issued together for room that fits only one -> exactly one admitted.
