Review report: `/home/nicoeft/workspace/webbzi/open-seo/.notebook/reports/T-0007-a1.md`. Fix F1, F2 (rename only), F4 and F5 exactly as below. Design: decision `dataforseo-project-ledger`.

## F1: request-level refusals in HTTP 200 bodies stay pending forever (must fix)

DataForSEO answers almost every error with HTTP 200 and an in-body `status_code` (40203 account cost limit, 40210 insufficient funds, 40202/40209 rate limits), plus a top-level `cost` (USD for that HTTP call). `assertOk` throws a plain `AppError` for those, so the self-hosted gate in `src/server/lib/dataforseo/client.ts` (`meterProjectDataforseoCalls`) settles them as `unknown`, and each attempt keeps its estimate against the project's limits forever.

Fix, self-hosted only, hosted untouched:
1. `src/server/lib/dataforseo/core.ts`: add `costUsd: number | null` to `DataforseoDispatch`; reset it to null with `status` before each attempt; in `requestDataforseo`, after the body parses, record the top-level `cost` into the dispatch store when it is a finite number >= 0.
2. `client.ts` self-hosted catch, in this order: a `DataforseoChargedTaskError` keeps its own billing; else if `dispatch.costUsd !== null`, settle `charged` at that cost (feature: `creditFeature` or, if null, mapped from the request path when available, otherwise left null); else the existing released/unknown rule.
3. Check whether the success path should also prefer the envelope cost: it should not change today's result for a normal success (`result.billing.costUsd`). Leave it.
4. Test: one more row in the existing `client.test.ts` dispatch table: fetch resolves 200 with `{"status_code":40203,"status_message":"...","cost":0,"tasks":null}` -> `charged` at 0. And one with a 20000 response that the fetcher then fails to parse, carrying `cost: 0.002` -> `charged` at 0.002.
