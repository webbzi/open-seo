## What changed and why

### `src/server/lib/dataforseo/client.ts` (the seam)
- **`ProjectBillingCustomer = BillingCustomerContext & { projectId: string }`** is exported from client.ts and re-exported from `index.ts`. `createDataforseoClient` requires it. The org-level `BillingCustomerContext` is unchanged.
- **Raw USD to the seam.** `meter(customer, operation, fetcher, estimateRawUsd, defaultFeature?)` and both batch entries pass raw USD estimates. `meterDataforseoCalls` converts them with `creditsForProviderUsd` only on the hosted branch, call by call. That is the same arithmetic as before, so hosted credits are identical.
- **Operation labels.** Every entry has an explicit label equal to its client path (`"serp.live"`, `"keywords.related"`, `"serp.rankCheckBatch"`, `"aiSearch.trackingLiveBatch"`, …). The label is passed to `admit`.
- **Self-hosted branch (`meterProjectDataforseoCalls`):**
  - Runtime assert of `projectId`, with a plain `Error`.
  - One `admit` per invocation, with one raw estimate per call and feature = `creditFeature ?? defaultFeature ?? null`.
  - A `PROJECT_BUDGET_EXCEEDED` / `PROJECT_DATAFORSEO_PAUSED` refusal returns every call as rejected with that AppError, and nothing is sent. Any other admission error (DB) propagates, and nothing is sent.
  - The calls then run with `Promise.allSettled`, followed by one `settle`:
    - success → `charged(result.billing.costUsd)`
    - `DataforseoChargedTaskError` → `charged(error.billing.costUsd)`, where 0 is a valid charge
    - provably unbilled → `released`
    - anything else → `unknown`
  - A cost that is not finite and ≥ 0 maps to `unknown`, so it cannot make `settle` throw for the whole batch.
  - When the admission feature is null, each charged outcome carries `mapDataforseoPathToCreditFeature(billing.path)`.
  - A failed `settle` is logged as `dataforseo.project-settle-failed` with `organizationId`, `projectId` and `usageIds`. It never throws.
  - The calls and the settle are registered with `waitUntil`, as on the hosted branch.
- **`keepAliveWithRequest`.** The `waitUntil` try/catch is extracted into this helper, which both branches use. On the hosted side this is a pure move of the same code and comment; nothing else on the hosted branch changed.
- **Max-lines.** The file now carries a reasoned `max-lines` disable, following the `serp.ts` / `subscription.ts` precedent. I chose this over splitting the two branches into separate files, because they mirror each other and read best side by side.

### `src/server/lib/dataforseo/core.ts`: how "provably unbilled" is proven
- `trackDataforseoDispatch(dispatch, run)` runs one metered call inside an `AsyncLocalStorage` scope. The repo already uses ALS for the pg client, and both workers have `nodejs_compat`.
- `createAuthenticatedFetch` sets `dispatch.sent = true` (and `status = null`) right before each `fetch`, and records `response.status` after it.
- The client releases a row only when nothing was sent or the last answer was an HTTP 4xx:
  - **Nothing sent** covers a missing API key and fetcher-side validation throws (`MAX_TASKS_PER_POST`, LLM group count, …).
  - **HTTP 4xx** covers classified and unclassified responses alike: 401, 402, 404, 429.
  - A network error after sending, a timeout, a 5xx (including after retries), and a parse failure on a 2xx all stay `unknown`.
- I chose this over tagging error objects. Classified 4xx errors are built by `createDataforseoBillingClassifier`, and pre-send throws happen in the fetchers, so tagging could not cover either. The ALS scope changes no error identity, so hosted error mapping is untouched.
- Hosted calls run with no store, so the tracking is a no-op for them.

- **Deserialized workflow payloads without `projectId`** (instances enqueued before deploy) now fail their paid calls with a plain Error instead of spending unmetered. That matches the brief.
