## 3. Existing refusal handling (by code)
Hosted-only pre-checks that throw `INSUFFICIENT_CREDITS` (never run self-hosted): `ProjectWebsiteService.ts:44-48`, `aiResearchKeywords.ts:117-120`, `aiPromptSuggestions.ts:66-69`, `RankCheckWorkflow.ts:105-122` (prepare step, `autumn.check`), `aiVisibilityRuns.ts:~97-120`, `rendering-billing.ts:32-50` (JS rendering lock, not DataForSEO), SamChatAgent `:335-345` (turn refusal "credits").

Per site, what happens on refusal:
- **`src/server.ts:201-251` scheduled()**: no code-specific handling. Runs `runScheduledRankChecks` and `runScheduledAiVisibility` under `Promise.allSettled`, rethrows first rejection at the end. `SCHEDULED_RANK_CHECKS_PAUSED` is a hosted-only kill switch for rank only.
- **`scheduledRankChecks.ts`**: schedule is claimed (`claimDueConfig`, `nextCheckAt` advanced, `lastSkipReason: null`) *before* `beginRankCheckRun` (`:154-181`). Skip reasons written here: `no_keywords` (`:114-120`), `plan_required` (`:140-148`). No credit/budget check at dispatch; hosted credits are only checked inside the workflow. If the run is "already running", the claim is **restored** (`:206-226`), i.e. schedule not advanced. Workflow start failure leaves schedule advanced (`:182-196`).
- **`RankCheckWorkflow.markRankCheckRunFailed` (`:258-281`)**: on a *thrown* run error with `INSUFFICIENT_CREDITS` sets `lastSkipReason: "insufficient_credits"` (`:267-274`); `failRunIfActive` always. Only the `prepare` step's hosted check throws that way. Errors inside batch steps do **not** reach this: `runLiveCheck`/`runQueuedCheck` exceptions are caught in `run()` (`:~377-387`) → `batchError`, run continues to `finalizeRankCheckRun`.
- **`RankSkipReason` type**: `"plan_required" | "no_keywords" | "insufficient_credits"` (`src/shared/rank-tracking.ts:138-141`); DB column free text (`app.schema.ts:237`). UI compares literals: `RankTrackingDomainList.tsx:261-267`, `RankTrackingDomainDetail.tsx:241`. `get-rank-tracker.ts:76` prints raw.
- **`rankCheckPaths.checkBatchLive` (`:84-135`)**: `rankCheckBatch` rejection (or whole-batch throw) → each pair `rejected`; code from `AppError.code`; `firstError` (bare code if `UPSTREAM_UNAVAILABLE`, else message) stored via `setRunErrorIfEmpty` (`:129`); other results still saved. Any rejected code is logged at `console.error` (non-`UPSTREAM_UNAVAILABLE`). No refusal-specific stop; **every subsequent batch step keeps calling the gate**.
- **Live→queue fallback (`runLiveCheck` `:151-228`)**: a live-batch step throw is warned and swallowed (`:176-182`); then `find-missing` diffs snapshots and re-runs `runQueuedCheck(..., liveFallback:false, saveNotFound:false)` for every missing pair — i.e. **a refused live batch triggers fresh queued `task_post` attempts** (up to 100 tasks per post).
- **Queue→live fallback (`runQueuedCheck` `:~360-480`)**: a failed `task_post` chunk (any error, incl. a refusal) → `fallback.push(...chunk)` (`:390-396`), then `stragglers` (fallback + pending) go to live `checkBatchLive` in batches of `KEYWORDS_PER_BATCH`=10 (`:469-478`) unless `liveFallback === false`. Scheduled runs use `runQueuedCheck` with default `liveFallback` (true per comment `:450-463`), so a refused post becomes a refused live call; no error-type discrimination.
- **`finalizeRankCheckRun` (`:~140-245`)**: status `failed` if 0 keywords checked else `completed` with partial message `Checked X of Y …: <keywordError>`; on `completed` clears `lastSkipReason` (`:215-218`); failed run leaves it. Schedule is not touched (advanced earlier).
- **`serverFunctions/rank-tracking.ts:188-199` `logAutoActionFailure`**: `PAYMENT_REQUIRED`/`INSUFFICIENT_CREDITS` → `console.info` skipped; else `console.error`. `runAutoCheck` (`:201-212`) returns null on any throw. Used for auto-check and auto-metrics-refresh after adding keywords (`:225-247`); new refusal codes would hit the `console.error` branch and be swallowed.
- **Scheduled AI (`scheduledAiVisibility.ts:22-90`)**: claims due tracker first (`claimDueTracker`, advances `nextCheckAt`, `lastSkipReason:null`, `:44-58`); `startRun(config,"scheduled",{userId:"system",…})`. Catch: `INSUFFICIENT_CREDITS` → `continue` (startRun already wrote `lastSkipReason:"INSUFFICIENT_CREDITS"`, `aiVisibilityRuns.ts:113-118`); `AiVisibilityError` → `lastSkipReason = error.message`; any other error → `lastSkipReason = "The scheduled check could not start."` + `console.error`. Schedule is advanced in all cases. `aiVisibilitySchedule.ts:62-70`: enabling the schedule's baseline run swallows `RUN_IN_PROGRESS` and `INSUFFICIENT_CREDITS` (schedule saved).
- **AI workflow (`AiVisibilityWorkflow.ts`)**: `postAiBatch` (`aiVisibilityCollection.ts:143-176`) catches any post error, stores `asAppError(cause)?.code ?? "INTERNAL_ERROR"` as the observation failure code for un-posted answers, never throws, no fallback to live. `collectAiLiveBatch` (`:186-220`): per-answer rejection → `{status:"failed", code, retryable:false}` (`:259-265`) → saved as failed, not retried (retry only when `retryable`, i.e. provider 5xx). `collectAiModelBatch` (`:~268-318`): retries only `DataforseoChargedTaskError` with `UPSTREAM_UNAVAILABLE` (≤ `AI_ANSWER_ATTEMPTS`); anything else → `failPendingObservations(runId, code, [tag])`. Reposts (`:96-125`) go through `postAiBatch` again (own paid attempt each). `finalizeAiRun` (`:424-440`): status completed/partial/failed from counts; on non-failed clears `lastSkipReason`; `markAiRunFailed` (`:443-447`) sets `lastSkipReason = AI_ANSWER_FAILURES.runFailed`. `lastSkipReason` is free text; UI special-cases only `"INSUFFICIENT_CREDITS"` (`PromptTrackingPage.tsx:232-241`), else shows `Most recent scheduling notice: <text>`.
- **Dashboard/background refresh `DashboardCacheService.readThrough` (`:11-72`)**: cache fresh → return. Else `DataRefreshClaimRepository.claim`; claim denied → stale cache with `refreshError:"Update already running or temporarily paused."` or `RATE_LIMITED` if no cache. On `load()` error: `finish(key, token, 5*60_000)` (5-minute backoff), returns cached value with `stale:true, refreshError: asAppError(error)?.code ?? "UPSTREAM_UNAVAILABLE"`; if no cache, rethrows. Cache TTL kept 90 days. UI: `siteTabParts.tsx:15-31` prints `getStandardErrorMessage(new Error(refreshError))` and an "Add credits" link only for `INSUFFICIENT_CREDITS`. `getLinkActivity` explicitly avoids a second charge when stale (`DashboardSiteService.ts:~118`).
- **Catch-blocks that turn errors into empty/partial data**:
  - `brandLookup.ts:~360-398`: `settle()` + `fulfilledOr()` converts rejections to `{status:"error", items:[]}`; `rethrowIfBlockingAiSearchError` rethrows only `INSUFFICIENT_CREDITS`/`AI_SEARCH_BILLING_ISSUE`. New codes would be **swallowed into empty data**.
  - `promptExplorer.ts:335-352` `mapErrorToResult`: rethrows only those two codes; everything else becomes `{status:"error", errorCode:"UPSTREAM_ERROR", message:"This model is temporarily unavailable…"}`.
  - `aiPromptResearch.ts:196-205`: `.catch` swallows only `UPSTREAM_UNAVAILABLE` for the SERP leg; others rethrown.
  - `research.ts:112-166`: `Promise.allSettled` for suggestions/ideas then rethrows the rejection (no swallow); `related` fallback is a third paid call only when blended rows are thin.
  - MCP `get-serp-results.ts:206-213` and `research-keywords.ts:180-187`: per-item `{ok:false, error: toolErrorMessage(error)}`; the refusal text becomes the per-item message.
  - `websiteResearch.ts:223-247`: per-query failure → `{keyword, error:"Live search failed…"}`; `searchOutage` only for all-`UPSTREAM_UNAVAILABLE`; throws "Website research was incomplete" if nothing succeeded and no outage (`:~340`) — a refusal there would surface as INTERNAL_ERROR.
  - `aiVisibilityCollection.collectAiLiveBatch` swallows per-answer save errors (`:~207-214`) but not refusals.
- **MCP `src/server/mcp/instrumentation.ts:204-220` `agentFacingError`**: *this* is where `INSUFFICIENT_CREDITS` is rewritten for agents ("Retrying won't help until the organization has more credits"); other codes pass through unchanged. `tool-error-message.ts:8-17` handles only `UNKNOWN_LOCATION` and `UPSTREAM_UNAVAILABLE` (no INSUFFICIENT_CREDITS).
- **Error codes**: `src/shared/error-codes.ts:3-24` (enum), `:33-48` `NON_REPORTABLE_ERROR_CODES` (INSUFFICIENT_CREDITS is non-reportable). `toClientError` (`src/server/lib/errors.ts:25-27`) returns `new Error(code)`; message never reaches the browser. `src/client/lib/error-messages.ts:19-20` is `Record<ErrorCode,string>` (exhaustive — a new code forces an entry). ## 4. Workflow DB scope
- `pgStep` = `step.do(name, cfg, () => withPgClient(fn))` (`pgStep.ts:21-29`); `withPgClient` is a no-op in D1 mode, reentrant, creates one `postgres(max:1)` client per scope in Postgres mode (`db/pg/client.ts:63-87`). ALS does not cross `step.do`.
- `pgDb` outside a scope: the Proxy `get` throws a plain `Error("Postgres database accessed outside a request scope…")` (`db/pg/client.ts:30-43`) — not an `AppError`, so `asAppError` yields null → INTERNAL_ERROR. `runBatch` in PG mode does `pgDb.transaction(...)` (`db/runBatch.ts:25-40`), so it throws that same error outside scope; in D1 mode it uses `d1Db.batch`. Any property access on `pgDb` triggers it, including building statements.
- Paid calls, all inside `pgStep`:
  - Rank: `live-batch-N` (`rankCheckPaths.ts:163-175`), `fallback-batch-N` (`:473-478`), `post-tasks-N` (`:376-388`), via `ctx.client` created at run-scope (`RankCheckWorkflow.ts:360`, lazy, no DB) but invoked inside step callbacks. `RankCheckWorkflow.run` also wraps `withPgClient(runScoped)` (`:296`). Step configs: `SINGLE_ATTEMPT_STEP_CONFIG` (retries 0, timeout 2 min, `rankCheckPaths.ts:~20`).
  - AI: `research-setup` (`AiVisibilityWorkflow.ts:68-77`, retries 0, 5 min), `live-N`, `post-N`, `model-N`, `repost-*` — all `pgStep`. `AiVisibilityWorkflow.run` does **not** itself call `withPgClient`; DB access is only valid inside `pgStep` (the `collect` closure and orchestration code outside steps touch no DB).
  - Site audit Lighthouse: `lighthouse-fetch-N` is `pgStep` (`siteAuditWorkflowPhases.ts:231-240`, `LIGHTHOUSE_FETCH_STEP` retries 0, 5 min, `auditStepConfigs.ts:28-31`); `SiteAuditWorkflow.run` is `withPgClient` wrapped (`:57`).
- Non-workflow paid paths: `fetch` handler wraps `withPgClient` (`server.ts:135`); cron wraps each scheduler (`:246-251`); SAM tool handlers wrap (`samChatTools.ts:166`). The shared client's `waitUntil(work)` (`client.ts:~405-412`) keeps provider call + settlement running after the response; whether a Hyperdrive socket remains usable after the request ends for settlement writes: **not confirmed** (code comment says socket is reclaimed when invocation ends, `pg/client.ts` header/`withPgClient` doc).
- Entry paths where `step` is absent (MCP, server fns, cron) are inside `withPgClient` from the entrypoint.

## 6. Batch sizes
- `serp.rankCheckBatch`: sole caller `checkBatchLive` (`rankCheckPaths.ts:90`). Live path: `KEYWORDS_PER_BATCH = 10` keywords (`src/shared/rank-tracking.ts:34`) × devices ("both" → 2) = **max 20 calls** per batch (`rankCheckPaths.ts:156-160`, `expandToTaskInputs :57-70`). Queue-straggler fallback slices *tasks* by 10 → max 10 calls (`:469-471`).
- `aiSearch.trackingLiveBatch`: sole caller `fetchLiveAnswers` (`aiVisibilityCollection.ts:229`); `LIVE_ANSWERS_PER_STEP = 6` (`:58`) → **max 6 calls** (retry rounds ≤ the same subset).
- `task_post`: `MAX_TASKS_PER_POST = 100` (`shared/rank-tracking.ts:49`, enforced `serp.ts:231`, `ai-tracking.ts:102`); rank chunks of 100 (`rankCheckPaths.ts:371-373`), AI `engineBatches(answers, MAX_TASKS_PER_POST)` (`aiVisibilityCollection.ts:~120`).
