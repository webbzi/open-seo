### Admission mechanics (decision Option 2, followed exactly)
`admit` runs one `runBatch`:
1. **Ensure the budget row:** `INSERT … SELECT FROM projects WHERE id AND organization_id … ON CONFLICT DO NOTHING`.
2. **Take the per-project lock:** `UPDATE … SET reservation_version = reservation_version + 1`, org-scoped.
3. **Conditional insert:** `INSERT … SELECT … FROM (VALUES (id, CAST(est AS double precision)), …) AS batch WHERE EXISTS(<budget not paused AND, for each non-null limit, committed < limit AND committed + batchTotal <= limit>) ON CONFLICT DO NOTHING`.
   - Committed is computed in SQL as `SUM(CASE status WHEN 'pending' THEN estimate WHEN 'completed' THEN cost ELSE 0 END)`; the month figure only counts rows with `started_at >= monthStart`.
   - Follow-on chunks use `WHERE EXISTS(first row id)`.
   - The decision is made in SQL, after the lock.

Then the service reads back the first id, org-scoped.
- **Present:** the batch was admitted.
- **Absent:** a second read only names the reason: project not in the org → `NOT_FOUND`, paused → `PROJECT_DATAFORSEO_PAUSED`, otherwise → `PROJECT_BUDGET_EXCEEDED`.
- **Database errors** propagate untouched; they are never turned into a refusal.

**Chunking.** `USAGE_ROWS_PER_INSERT = 40`. The deciding statement binds 12 + 2 per row (92 at most); a follow-on binds 7 + 2 per row.
- The largest live batch the client sends today is 20 calls: `rankCheckBatch` = `KEYWORDS_PER_BATCH` 10 × 2 devices; `trackingLiveBatch` is 6. Both fit in one statement.
- The test uses 100 calls so the chunk path (3 statements) actually runs. The test `runBatch` checks every statement's bound parameters against D1's limit of 100; SQLite alone would not catch this.

**`updateBudget`** checks the project (org-scoped, archived included), then runs `ensureBudget` + an `UPDATE` that also bumps `reservation_version`. It takes the same row lock as admissions.

**`settle`** runs one guarded `UPDATE` per outcome (`id`, `project_id`, `status='pending'`, org-scoped) in one batch. `unknown` writes nothing; if every outcome is `unknown`, there is no DB call at all. A provided feature only fills a NULL: `COALESCE(feature, ?)`.

**Retries (`withQueryRetries`).** `runBatch` on Postgres goes through `db.transaction` → `sql.begin`, and that connection-scoped client bypasses the retry proxy (it only wraps `sql.unsafe`). So no statement inside an admission is ever replayed, and the transaction cannot be broken by a retry. The read-backs are SELECTs, which the wrapper retries safely.
- Ids are fresh `crypto.randomUUID()` values per `admit()` call, and the inserts carry `ON CONFLICT DO NOTHING`, so replaying the same ids could not double-insert either.
- If the read-back fails after a commit, `admit` throws an infrastructure error. The committed rows stay pending and later show as estimated, which is a conservative overcount.

**Why statement 3 sees a competing admission's rows on Postgres (READ COMMITTED).**
- Statement 2 takes the row lock on the budget row. A competing transaction blocks at its own statement 2 until the holder commits; Postgres then re-checks the updated row and proceeds.
- Statement 3 is a new statement, and under READ COMMITTED each statement takes a fresh snapshot when it starts. That snapshot therefore includes the usage rows the lock holder committed.
- For a project with no budget row yet, statement 1's `ON CONFLICT DO NOTHING` waits on the other transaction's uncommitted insert of the same key, then does nothing. It does not deadlock, because both transactions take locks in the same order.

### Choices I made where the brief was open
- **`featureBreakdown` is all-time**, so it adds up to `totalRecordedUsd` / `estimatedUsd`. Features with zero recorded and zero estimated are dropped; the rest are sorted by recorded, largest first.
- **When both limits are reached, status is `total_limit_reached`.** It is the one a new month will not reset. Reached means committed ≥ limit, the same rule admission uses.
- **`configured` means `updated_by_user_id IS NOT NULL`,** as the brief says.
- **`availableUsd`** = max(0, min over configured limits of (limit − committed)); null when unlimited.
- **The summary's month is `[monthStart, nextMonthStart)`** so a `now` parameter in the past works. Admission uses `>= monthStart`; the two are the same for the real current time.
- **Export** returns rows started in `[from, to)`, oldest first, archived projects included. Each row has `status` (the derived `estimated` included), `estimatedCostUsd` and `costUsd`, so recorded and estimated amounts can be told apart.
- **Recent usage** is newest first, with paging limited to 1–100 rows.
- **Archived projects can still admit and be configured.** The ledger does not gate on archival; whether archived projects can make paid calls is a question for the caller (T2).
- **A missing project and another org's project behave the same:** `admit`, `getProjectSummary` and `updateBudget` throw `NOT_FOUND`; `listRecentUsage` returns `[]`; `settle` is a silent no-op.
- **An empty `estimatesUsd`** returns `{ usageIds: [] }` without touching the DB.

### Contract

## Open points / risks
- **Floating-point noise.** Plain JS numbers, as specified. Postgres sums show values like `inFlightUsd: 2.47999999999999`, and at an exact boundary a batch that fits on paper can be refused by about 1e-15. The UI (T3) should round for display. I did not add an epsilon, because the rule as written is exact.
- **No foreign key on `actor_user_id` / `updated_by_user_id`.** The scheduled-work actor convention may not be a real user id. These user ids are not covered by `scripts/erase-user-data.ts`; flagging for GDPR review, not fixed (outside this task).
- **`INSERT … SELECT` uses raw SQL with positional columns,** following the `ProjectWebsiteRepository` precedent: drizzle's builder form would not type-check against the `d1Db`-typed tx. The column order is documented at both call sites, and the tests read back every column, so a misordered column would fail them.
- **The notebook context and the code agree;** I found no discrepancy.
