## Result

### F1: request-level refusals in HTTP 200 bodies are no longer left pending forever
- `src/server/lib/dataforseo/core.ts`
  - `DataforseoDispatch` gains `billing: DataforseoApiCallCost | null`.
  - It is reset to null together with `status` before each attempt.
  - After `requestDataforseo` parses a body, it records the top-level `cost` there when that is a finite number >= 0, along with the request path split into segments.
  - Bodies that are empty or unreadable record nothing.
  - `dataforseoPostResponse` (Lighthouse) never parses a body here, so it records nothing and behaves as before.
- `src/server/lib/dataforseo/client.ts`: the self-hosted catch moves into `failedOutcome`, applied in this order:
  1. A `DataforseoChargedTaskError` keeps its own billing.
  2. Otherwise, a recorded envelope cost settles the row `charged` through the existing `chargedOutcome`, with feature = `creditFeature`, else mapped from the request path.
  3. Otherwise, the old released/unknown rule.
- **Deviation from the brief:** I used `billing: {path, costUsd}` instead of a bare `costUsd: number | null`.
  - Why: the brief asks for the feature to be "mapped from the request path". The dispatch only has the path if it records it.
  - `DataforseoApiCallCost` is exactly the shape `chargedOutcome` already takes, so the feature mapping and the finite-cost guard are reused, not duplicated.
  - Semantics are otherwise the brief's.
- Success path (brief step 3): left as is. For one-task live calls, `result.billing.costUsd` (task cost) equals the envelope cost. The task_post fetchers already sum their entries. Preferring the envelope would change nothing today.
- Hosted mode: untouched. It never calls `trackDataforseoDispatch`, so `dispatchStore.getStore()` is undefined and nothing is recorded.

## Attention
- "Unknown" now covers only bodies without a usable top-level `cost`: transport failures, timeouts, 5xx and unparseable bodies. DataForSEO documents `cost` on every response, so a refusal that omits it would still stay pending. I have not seen evidence that this happens.
- If a single metered fetcher ever made two requests, the dispatch would keep only the last request's envelope cost, like `status` today. I checked: no metered fetcher does that, and none calls a free GET inside its scope.
- Decision `2026-10-15-dataforseo-project-ledger` is still marked proposed. This work builds on its Option 2, as the brief directs.
