# T-0007 RV1: Merge-ready review of per-project DataForSEO budgets

Mode: review. Target: `git diff main...feat/dataforseo-project-budgets` (691bff3c, merge base 3d45410f; commits T-0001, T-0003, T-0004, T-0005, T-0006). Read-only. No source edits.

## Verdict

**Not merge-ready. One High finding needs a small fix first.** The ledger core works. The admission SQL takes the per-project lock, checks the limits in SQL and admits a batch whole or not at all. Settlement is idempotent. Tenant scoping is correct throughout. Hosted billing is unchanged. The bug is in settlement classification. DataForSEO reports request-level refusals inside an HTTP 200 body, and the self-hosted gate files each of those as "unknown". There is no expiry and no cleanup, so each refused attempt leaves a pending row that counts its estimate against both limits forever.

The most likely trigger is the DataForSEO account-level daily cost cap, the safety net the plan tells the agency to keep. Once it trips, every paid attempt in every capped project burns allowance for calls that cost nothing. The fix is about 15 lines in `core.ts` and `client.ts` and leaves hosted mode untouched. Merge after it; everything else can follow.

- In scope: the server ledger (schema, migrations, repository, service, client gate, `core.ts` dispatch tracking), every paid call path the plan lists, workflows, server functions, routes and hosted surfaces, and the tests the branch adds.
- Only skimmed: the React UI components under `src/client/features/api-spending/**`. I checked copy and gating, not layout.
- Basis: the code wins over the notebook. Decision `2026-10-15-dataforseo-project-ledger` is still marked **proposed** (the owner has not chosen). The branch builds Option 2 from it, and I review against Option 2 plus the owner's plan.

  - The API "always return[s] the 200 HTTP response code" except 401, 402, 404 and 500 ([errors appendix](https://docs.dataforseo.com/v3/appendix/errors/)).
  - The top-level response field `cost` is "total tasks cost, USD" ([SERP live advanced](https://docs.dataforseo.com/v3/serp/google/organic/live/advanced/)).
- Postgres semantics were reasoned from engine behaviour and the `ProjectWebsiteRepository` INSERT…SELECT precedent. They were not executed: the repo has no Postgres test infrastructure.

## Critical findings

### F1 — High: request-level refusals in HTTP 200 bodies leave a pending row at its estimate forever

**Location:** `src/server/lib/dataforseo/client.ts:540-552` (self-hosted catch), with `src/server/lib/dataforseo/envelope.ts:269-275` (`assertOk`, top-level branch) and `src/server/lib/dataforseo/core.ts:214-219` (`requestDataforseo`).

**Causal chain:**
1. DataForSEO refuses at request level with HTTP 200 and an in-body code: 40203 (account cost limit exceeded), 40202 (rate limit), 40209 (too many simultaneous requests) or 40210 (insufficient funds).
2. `requestDataforseo` parses the body and returns it. `core.ts:131` records `dispatch.status = 200`.
3. `assertOk` sees `status_code !== 20000` and throws a plain `AppError` (classified, or `failedResponseError`), not a `DataforseoChargedTaskError`.
4. In `meterProjectDataforseoCalls`, `unbilled` is false (the call was sent and the status is not 4xx), so the outcome is `"unknown"`.
5. `settle` writes nothing. The row stays `pending` and counts its `estimatedCostUsd` in both the monthly and total sums.
6. Nothing ever moves it (Option 2 has no expiry and no cleanup). After 30 minutes the UI shows it as "estimated".

`postRankCheckTasks` (`serp.ts:264-266`) and the other task_post fetchers reach the same `failedResponseError` path.

**When it fires:**
- The agency's DataForSEO account hits its daily cost cap (plan: "Keep DataForSEO's account-level cap as an independent safety net").
- The account balance runs out.
- Bursts trip 40202 or 40209.

From then on, every paid attempt in every project adds phantom spend:
- **Manual rank checks:** live estimates for every keyword/device pair. Because none were refusals, `runLiveCheck` then sends the queue fallback, which adds the task_post estimate for the same pairs.
- **Dashboard cards:** a re-attempt every 5 minutes per card through `DashboardCacheService`.
- **AI runs:** estimates of $0.10 or more per mentions call.

**Blast radius:**
- Every capped project during any provider-side refusal window.
- The monthly allowance drains with $0 actually spent. After the agency tops up DataForSEO, projects still read "Monthly limit reached" until the next UTC month.
- The total-project limit is reduced permanently.
- The only remedy is hand-written SQL against the ledger, and nothing documents it.

The same path also covers the known `parseTaskItems` debt (review-guidelines false-positive controls). A 20000 response that DataForSEO billed, but whose items fail Zod validation, stays pending at the estimate even though the exact cost was in the body.

**Why this contradicts the design:** the decision limits "unknown" to "transport, timeout, 5xx, parse failure without envelope". A parsed response with a top-level `cost` is not ambiguous. DataForSEO told us exactly what it charged.

**Fix (smallest correct, hosted untouched):**
1. Add `costUsd: number | null` to `DataforseoDispatch`. Reset it to `null` with `status` on each attempt (`core.ts:100-103`).
2. In `requestDataforseo`, after `JSON.parse` (`core.ts:217`): `const dispatch = dispatchStore.getStore(); if (dispatch && typeof parsed?.cost === "number" && Number.isFinite(parsed.cost)) dispatch.costUsd = parsed.cost;`
3. In the self-hosted catch (`client.ts:549-551`), use this order:
   - a `DataforseoChargedTaskError` keeps its own billing;
   - else, when `dispatch.costUsd !== null`, the outcome is `{ kind: "charged", costUsd: dispatch.costUsd }` (feature: `creditFeature`, or null);
   - else, the existing `released`/`unknown` rule applies.
4. Add one row to the existing `it.each` in `client.test.ts`: fetch resolves `200` with `{"status_code":40203,"cost":0,"tasks":null}` and the expected outcome is `{ kind: "charged", costUsd: 0 }`.

**Second-order effects:**
- "Unknown" shrinks to what is genuinely ambiguous: transport failures, timeouts, 5xx, unreadable bodies and Worker death.
- Billed parse failures settle exactly instead of at the estimate.
- Lighthouse (`dataforseoPostResponse`, body read later) keeps today's behaviour.
- The hosted branch never reads the dispatch record.

**Effort:** quick.

### F2 — Low-Medium: the Postgres admission path has no executed evidence, and the "concurrent" test cannot fail for its named reason

**Location:** `ProjectDataforseoBudgetService.query.test.ts:203` ("lets only one of two concurrent admissions take the last room"); `ProjectDataforseoRepository.ts:97-176`.

**What the test can and cannot prove:** the query tests run on in-memory libsql. One client means `db.batch` calls run one at a time, so two "concurrent" admits are sequential. If `lockBudget` were deleted, or moved after the insert in the batch, this test would still pass. It does prove one real thing: a pending estimate counts against the next admission.

**Where the lock matters:** only on Postgres. Under READ COMMITTED, the second transaction blocks on the `UPDATE … reservation_version + 1` row lock. Its following `INSERT … SELECT … WHERE EXISTS(SUM …)` then takes a fresh snapshot that includes the first transaction's rows.

**By analysis the Postgres SQL is correct:**
- Unknown params in the INSERT…SELECT target list are coerced to the target column types (same pattern as `ProjectWebsiteRepository`, already in production).
- `VALUES` columns are named `column1`/`column2` on both engines.
- `false`, `0` and `NULL` coerce in `ensureBudget`.
- `committed` is a non-reserved keyword, valid as an alias.

But nothing executes it, and the plan's acceptance criterion explicitly asked for Postgres.

**Blast radius:** admission is always on in self-hosted mode; there is no flag. A Postgres-only SQL error would fail every paid DataForSEO call on Postgres self-hosts. It would fail closed: an infra error, not overspend. Separately, the lock-before-insert ordering is guarded only by a comment. A regression there would silently allow overspend on Postgres.

**Fix:**
- Rename the test to what it proves ("counts a pending admission against the next").
- Before announcing the feature to Postgres self-hosters, do a one-time manual check: two `psql` sessions, each running BEGIN, lock UPDATE, conditional INSERT, with the first held open.
- Adding PGlite for dialect coverage would catch type and coercion errors but still not row-lock concurrency (single connection). That is a new dependency, so it is the owner's call; I don't recommend it for this PR.

**Effort:** quick for the rename plus the manual check.

### F3 — Low: no documented way to correct a stuck row or enter an opening balance

**Location:** no file. Both are hand-SQL procedures by design (decision: "Opening balances are inserted by hand as `completed` rows"). Neither `docs/` nor `web/content/docs/` changed in this branch.

**Scenario:** an agency client is halfway through a retainer at deployment, or a genuinely ambiguous call (a timeout) sits "estimated" and the owner confirms its real cost in the DataForSEO `id_list`. The operator has no documented, dialect-safe statement for either. They have to reverse-engineer the column order and the `status` and `operation` literals, and they risk a malformed row that the admission SUM then counts. After F1, "estimated" rows become rare, so this is about documentation only.

**Fix:** add a short self-hosting docs section with two statements that work on both dialects:
- an `INSERT` for an `opening_balance` completed row;
- an `UPDATE … SET status='completed', cost_usd=?, completed_at=? WHERE id=? AND status='pending'`.

**Effort:** quick.

### F4 — Low: the refusal copy says "reached" when the request merely doesn't fit

**Location:** `src/client/lib/error-messages.ts:21`, `src/server/mcp/tool-error-message.ts:17`.

**Scenario:** a project has $0.10 left of its monthly limit and a $0.20 request is refused. Admission correctly refuses, because committed + batch > limit. The app says "This project's DataForSEO allowance has been reached", while the API spending tab shows "Available $0.10" and status "available" (`budgetState` reports reached only once committed ≥ limit). The MCP text says the allowance is "used up" and that "Retrying this or another paid operation won't help", which is false for cheaper operations. This happens at the end of every month for every capped project, and batch admission (rank checks: 20 calls refused whole) makes it more visible.

**Fix:** copy only. For example: "This project doesn't have enough DataForSEO allowance left for this request. Review API spending in project settings." In the MCP text, replace "used up" with "too low for this request".

**Effort:** quick.

### F5 — Low: `runId` is never recorded

**Location:** `client.ts:499-505`. `admit` accepts `runId`, but `meterProjectDataforseoCalls` never passes it, and `ProjectBillingCustomer` doesn't carry it.

**Impact:** the plan's coverage table asks for "project context and run ID". As built, `run_id` is null on every real row and the CSV export column is always empty, so a run cannot be matched to its spend when investigating a surprise charge. Investigation metadata only; no money impact.

**Fix:** add an optional `runId` to `ProjectBillingCustomer` and set it in the rank check, AI visibility and site audit workflow payloads (each already has the id). Otherwise, drop the column from the export until it is needed.

**Effort:** scoped. It touches workflow payload shapes, and those must stay optional for runs in flight across the deploy.

## Brief checklist results (no finding)

**1. Money correctness**
- Two admissions cannot spend the same room. On D1 the batch is atomic and serialized. On Postgres the row lock, then a fresh READ COMMITTED snapshot for the conditional insert, prevents it.
- Batches spanning several insert statements land whole, because follow-on statements are conditioned on the first row existing. Every statement stays at or under 92 bound parameters.
- No raw paid import bypasses the gate in app code. Remaining raw imports are free task_get collection, the sandbox `probeSerpLocation`, types and schemas, and operator `scripts/`.
- Hosted website research still collects cost for `billResearchSpend`. Self-hosted research goes through `client.serp.live`, one admission per attempt including each 40101 retry.
- `postRankCheckTasks` now has `maxServerErrorRetries: 0`.
- task_post costs are summed once over the entries; the top-level total is never added on top.
- Settlement is guarded by `status = 'pending'`, so a duplicate settle is a no-op.
- DB errors at admission propagate as infra errors and nothing is sent. NOT_FOUND (foreign or missing project) is not mislabelled as a refusal.
- The one residual mislabel is F1 (a provably unbilled call is treated as unknown).
- Accepted by the decision, and still awaiting owner sign-off since it is "proposed": an HTTP 5xx on a live read can be retried up to twice under one row. If DataForSEO ever billed a 5xx, that charge would be missed.

**2. Hosted regression: none found.**
- The `meterDataforseoCalls` hosted branch is byte-equivalent: credits are computed from the same raw estimate, the only refactor is `keepAliveWithRequest`, and `INSUFFICIENT_CREDITS` handling is unchanged.
- In `websiteResearch`, the hosted branch keeps the same spend records in the same order.
- `rankCheckPaths` and `AiVisibilityWorkflow` compute the same values when `refusal` is null. Step names are unchanged; `fail-refused` runs only on a refusal.
- `markRankCheckRunFailed` now uses `asAppError`, which can only add detection; the hosted credits message is not a bare code, so behaviour is identical.
- Two harmless hosted-visible changes:
  - the MCP `get_rank_tracker` skip-reason column now prints readable text for the existing reasons;
  - `failPendingObservations` now chunks ids for D1's bound-parameter cap.

**3. Tenant scoping and authorization: all good.**
- Every ledger statement is scoped through `projects.organization_id`, including settle and the reads; another organization's project behaves exactly like a missing one.
- Server functions take the organization and project from middleware context.
- Limit changes and CSV export require `billing: ["manage"]`.
- All five server functions return NOT_FOUND in hosted mode, and both routes call `notFound()` in hosted mode, with their tabs hidden.
- The MCP billing customer is built after `withMcpProjectAuth` verifies the project.

**4. Dual dialect: good by analysis** (see F2).
- Both migrations match: `real` ↔ `double precision`, `integer` boolean ↔ `boolean`, the same FKs with cascade, the same index.
- ISO timestamp defaults on both dialects make lexicographic month comparisons valid.
- Workflow DB access sits inside `pgStep`.
- On Postgres, settlement inside `waitUntil` runs in the creating ALS scope, and the caller awaits it.
- The D1→Postgres migration script discovers tables from the schema, so it picks up both new tables.

**5. Refusal semantics: all good.**
- Schedules advance through the existing claim logic (rank: the cron advances eagerly; AI: `claimDueTracker` runs before `startRun`), and each records a distinct skip reason.
- Refused rank runs send no queue or live fallback and keep the snapshots they already saved. Refused AI runs stop posting and keep collecting tasks already posted.
- Lighthouse records a skipped check.
- Dashboard cards keep their cache, show the reason, and wait out a 5-minute cooldown.
- No app or MCP copy offers credits.

**6. Tests**
- Apart from F2, the new tests follow AGENTS.md: real SQL for the repository, the real request layer behind a stubbed `fetch` for dispatch classification, and mocked-collaborator assertions only where the mapping is the billing contract.
- Minor redundancy: the server-function test "neither reads nor writes another organization's project" repeats the service-level tenant test. In production, `requireProjectContext` rejects a foreign `projectId` before the handler, so that case can never reach it. Optional trim.

## Structural observations

- **The reframe behind F1:** the ledger tracks one row per HTTP call, and DataForSEO's top-level envelope `cost` is exactly the cost of one HTTP call. Settling from the envelope captured at the transport layer, not from per-feature task billing, removes the whole class of "the fetcher threw after a billed response" cases for self-hosted mode. Hosted mode could later use the same record to retire the `parseTaskItems` debt. That is out of scope here; it would change hosted metering.
- **`configured` piggybacks on `updatedByUserId !== null`** (`ProjectDataforseoBudgetService.ts:86`). That forced the GDPR erase script to write a `"gdpr-deleted-user"` sentinel instead of null. Today the cost is contained: enforcement reads the limits, never `configured`. But if anyone later nulls that column for privacy, the overview silently flips a project to "not configured". Not worth changing now; don't build anything else on it.
- **Always-on hot path.** Every self-hosted paid call now does one write batch (3+ statements), one read and one settle batch. The project's total committed spend is summed over all of its usage rows on each admission. The decision accepts this, and it is fine at agency scale. Revisit only if a project's row count passes about 100k.

## Worth preserving

- Admission in one `runBatch`: ensure row, row lock, then an SQL-side whole-batch check. Follow-on chunks are conditioned on the first row, and IDs are generated before the batch, so a retried transaction is idempotent.
- `ensureBudget` inside admission instead of creation hooks. It removes the "project created by a path that forgot the hook" class of bugs.
- Dispatch tracking through `AsyncLocalStorage` in the single authenticated fetch. "Nothing sent" and "HTTP 4xx" are classified from what actually happened on the wire, not from error types.
- The type-level `ProjectBillingCustomer` plus the runtime assertion for deserialized workflow payloads.
- Refusals carry the bare code as the message, so `stepProjectRefusal` survives workflow step boundaries.
