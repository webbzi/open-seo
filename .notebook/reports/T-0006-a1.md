## Design: how a refusal crosses a workflow step

- **Paid steps signal a refusal by throwing it, not through their return value.**
  - The persisted outputs of `live-batch-N`, `post-tasks-N`, `fallback-batch-N`, `post-N`, `live-N`, `model-N` and `repost-*` keep their old shape.
  - So a run that is in flight across the deploy still replays correctly. Changing the shape of a paid step's output would crash on replay, and renaming the step would re-post and re-bill.
  - The repo's own `read-*` rename comment shows this concern is real.
- **The orchestrator reads the refusal back with `stepProjectRefusal(error)`** (`src/server/workflows/projectRefusal.ts`), which is `isProjectDataforseoRefusal(asAppError(error))`.
  - The engine may return a step's error without its class.
  - Its message survives, and every refusal's message is its bare code: `admit` throws `new AppError(code)`, and so does the new pre-check.
  - The tests reject with `new Error("PROJECT_BUDGET_EXCEEDED")` to pin this.
- **Run-level refusal state is rebuilt from step outcomes on replay**, like `pending` in the AI workflow. It is never written inside a step.

## Open points and risks
- **Refusal detection across a step depends on `message === code`.** That holds for T-0004's `admit` and for the pre-check. If anyone gives those refusals a custom message, `stepProjectRefusal` stops recognising them after a real step boundary. In-process tests would still pass because they keep the class. I did not verify message survival on a real Workflows runtime; the CF docs show `e.message` in step catch blocks.
- **Pre-existing, not fixed (hosted): `markRankCheckRunFailed` used `instanceof AppError` for `INSUFFICIENT_CREDITS` thrown from the `prepare` step.**
  - If the engine strips the class, the hosted `insufficient_credits` skip reason has never been recorded.
  - Its message, "Insufficient credits for rank check", is not a code, so `asAppError` cannot recover it either.
  - Worth a check on hosted.
- **The rank detail hides `RankRunAlerts` while a project skip reason is set,** including its `maybeStale` warning for a newer run that is in progress. The reason clears when a run completes without a refusal.
- **Dashboard during the 5-minute backoff:** the denied claim shows "Update already running or temporarily paused." rather than the project reason.
- **MCP's "Latest run: failed — PROJECT_BUDGET_EXCEEDED" line prints the bare code.** It was out of scope; only the skip reason column was asked for.
- **`brandLookup` discards the lookup's other parallel results when one call is refused,** the same as for `INSUFFICIENT_CREDITS` today, per the brief.
- **Onboarding's `startWebsiteTrackingRun` still logs a refusal at warn.**
- **The decision `dataforseo-project-ledger` is still `proposed`.** This task depends only on the two codes and `getProjectSummary().status`, which T-0004 and T-0005 already ship. The notebook and the code agree.
- **No plugin version bump:** no new tool or skill.
- **Papercut not logged:** the missing `node_modules`, because `.agents/**` is off-limits for this task.
